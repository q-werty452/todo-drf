# todo-drf

Простое API для списка задач на Django REST Framework. Учебное, разбирался с APIView.

Задача это title, completed и created_at, больше ничего.
Вьюхи написаны на APIView, а не на ViewSet — специально, чтобы руками расписать все методы.

Пользователь свой: `users.CustomUser`, вход по email вместо username.
Авторизация по токену, задачи видит только их владелец.

## Запуск

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

`createsuperuser` спросит **email**, а не username — так работает `USERNAME_FIELD = "email"`.

## Ручки

```
POST   /api/register/    регистрация, отдаёт токен
POST   /api/token/       вход по email и паролю, отдаёт токен

GET    /api/todos/       список своих задач
POST   /api/todos/       создать задачу
GET    /api/todos/1/     одна задача
PUT    /api/todos/1/     заменить целиком
PATCH  /api/todos/1/     обновить часть полей
DELETE /api/todos/1/     удалить
```

Первые две открыты всем, остальные только с токеном.

# Как это работает (шпаргалка, потом удалить)

## Что такое токен

Аналогия — браслет в аквапарке. На входе один раз показываешь паспорт и платишь,
тебе выдают браслет с номером. Дальше у каждой горки охранник паспорт не спрашивает,
он смотрит на браслет и сверяется со списком: браслет №4471 — это Иванов, оплачен день.

| В аквапарке | В проекте |
|---|---|
| паспорт | email + пароль |
| касса на входе | `POST /api/register/` или `/api/token/` |
| браслет | токен, 40 случайных символов |
| список у охранника | таблица `authtoken_token` в базе |
| горки внутри | `/api/todos/` |

Что реально лежит в базе после входа — три поля, больше ничего:

```
key     = 9c4f7a2e1b8d3f6a0c5e7d9b2a4f6c8e0d1b3a5f
user_id = 4
created = 2026-08-13 06:35
```

Главное: **внутри токена нет ни email, ни пароля**. Это случайная строка.
Связь «токен → человек» хранится на сервере, в этой таблице. По перехваченному
токену пароль восстановить нельзя — там нечего восстанавливать.

## Что происходит при каждом запросе

1. Клиент шлёт заголовок `Authorization: Token 9c4f7a2e…`
2. Сервер берёт строку после слова `Token`, ищет её в таблице, получает `user_id`.
   Этот пользователь попадает в `request.user`.
3. Вьюха делает `Todo.objects.filter(owner=request.user)` — отдаются задачи
   только этого человека, чужие в выборку не попадают никогда.
4. Токена нет или он неверный → `401`, до кода вьюхи выполнение не доходит.

## Зачем это вместо логина с паролем каждый раз

- **Пароль передаётся реже.** Один раз при входе, а не в каждом из сотен запросов.
- **Токен можно отозвать.** Утёк — удалил строку в таблице, человек логинится заново.
  С паролем пришлось бы менять сам пароль.
- **Проверка дешевле.** Сверить токен — один поиск по индексу. Проверить пароль —
  намеренно медленное хеширование, в базе видно `pbkdf2_sha256$1200000$`,
  то есть 1 200 000 итераций. Гонять такое на каждый запрос нельзя.

# Демонстрация в Postman

Сервер должен быть запущен: `python manage.py runserver`.
Тело запросов — вкладка **Body** → **x-www-form-urlencoded**.

Слеш в конце адреса обязателен: `/api/todos/` работает, `/api/todos` — нет.

## 1. Регистрация

```
POST http://127.0.0.1:8000/api/register/
```

Body:

| ключ | значение |
|---|---|
| email | student@mail.ru |
| password | Tr0ub4dour-x9 |
| password2 | Tr0ub4dour-x9 |

Ответ `201 Created`:

```json
{
    "email": "student@mail.ru",
    "token": "9c4f7a2e1b8d3f6a0c5e7d9b2a4f6c8e0d1b3a5f"
}
```

**Скопировать токен** — нужен в шагах 5–7.

Сказать: регистрация сразу возвращает токен, чтобы не делать второй запрос на вход.
Пароль в ответе не появляется — в сериализаторе оба поля пароля помечены `write_only`.

## 2. Пароли не совпадают

Тот же адрес, но `password2` другой. Ответ `400`:

```json
{
    "password": ["Пароли не совпадают."]
}
```

Заодно можно показать слабый пароль — вписать в оба поля `123`, получится три ошибки
сразу: слишком короткий, слишком частый, только из цифр. Это стандартные валидаторы
Django из настройки `AUTH_PASSWORD_VALIDATORS`.

## 3. Запрос без токена

```
GET http://127.0.0.1:8000/api/todos/
```

Никаких заголовков — в этом смысл шага. Ответ `401 Unauthorized`:

```json
{
    "detail": "Authentication credentials were not provided."
}
```

Сказать: все эндпоинты закрыты по умолчанию, в настройках прописано
`DEFAULT_PERMISSION_CLASSES: [IsAuthenticated]`. Доступ открывается осознанно —
у регистрации стоит `AllowAny`, иначе зарегистрироваться мог бы только тот,
кто уже зарегистрирован.

## 4. Повторный вход

```
POST http://127.0.0.1:8000/api/token/
```

Body:

| ключ | значение |
|---|---|
| username | student@mail.ru |
| password | Tr0ub4dour-x9 |

Ответ `200 OK` — токен **тот же самый**, что при регистрации: он создаётся один раз
и живёт, пока его не удалят.

Поле называется `username`, а внутрь кладём email — так устроен готовый эндпоинт DRF,
имя поля у него зашито. Но в проекте своя модель пользователя с `USERNAME_FIELD = "email"`,
поэтому Django ищет человека именно по email. Это не ошибка, а стык стандартного кода
с кастомной моделью.

## 5. Создать задачу с токеном

```
POST http://127.0.0.1:8000/api/todos/
```

Headers:

| ключ | значение |
|---|---|
| Authorization | Token 9c4f7a2e1b8d3f6a0c5e7d9b2a4f6c8e0d1b3a5f |

Body:

| ключ | значение |
|---|---|
| title | Сделать домашку |

Ответ `201 Created`:

```json
{
    "id": 1,
    "title": "Сделать домашку",
    "completed": false,
    "created_at": "2026-08-13T06:20:27.827558Z"
}
```

Поле `owner` в запросе не передавалось. Владельца сервер проставил сам из токена —
в коде это `serializer.save(owner=request.user)`. Подделать чужое авторство через
тело запроса невозможно.

## 6. Список своих задач

```
GET http://127.0.0.1:8000/api/todos/
```

С тем же заголовком `Authorization`. Ответ `200 OK` со своей задачей в списке.

## 7. Второй пользователь чужого не видит

Самый убедительный шаг — показывает, что разграничение доступа реально работает.

Зарегистрировать второго (шаг 1 с другим email, например `petya@mail.ru`),
взять **его** токен и повторить с ним:

```
GET /api/todos/        ->  200 OK,  []          пусто
GET /api/todos/1/      ->  404 Not Found
```

Сказать: пустой список — потому что выборка фильтруется по владельцу. А на прямой
запрос чужой задачи приходит `404`, а не `403`, и это намеренно: `403` означал бы
«задача существует, но она не твоя» и подтвердил бы постороннему сам факт её
существования. `404` не выдаёт ничего.

## Если что-то не работает

| Симптом | Причина |
|---|---|
| `401` с токеном | потерялось слово `Token` или пробел. Формат строго: `Token 9c4f7a2e…` |
| `401` без заголовка | заголовок добавляется в **Headers**, не в Body. Проверить галочку слева от строки |
| `400` при регистрации | читать тело ответа, там написано какое поле не устроило |
| `404` на всё | потерялся слеш в конце или префикс `/api/` |
| Connection refused | не запущен `python manage.py runserver` |

# Полный прогон с нуля

Делать по порядку сверху вниз. Нужно **два окна терминала**: в первом работает
сервер и не закрывается, во втором вводятся команды.

## Шаг 0. Убить старые серверы

Если сервер уже где-то запущен, порт 8000 будет занят и новый не поднимется.

```bash
pgrep -af "manage.py runserver"
```

Если что-то нашлось:

```bash
pkill -f "manage.py runserver"
```

## Шаг 1. Окружение

```bash
cd ~/Desktop/todo-drf
source venv/bin/activate
```

В начале строки должно появиться `(venv)`. Дальше везде просто `python`, без
`./venv/bin/`.

## Шаг 2. Чистая база

Не обязательно, но так прогон получается честным — с нуля.

```bash
rm db.sqlite3
python manage.py migrate
```

Должно закончиться списком `Applying ... OK`. Обрати внимание на порядок:
`users.0001_initial` идёт **до** `admin.0001_initial` — так и должно быть,
потому что админка ссылается на модель пользователя.

## Шаг 3. Суперюзер

```bash
python manage.py createsuperuser
```

Спросит **Email address**, а не Username — это и есть работа `USERNAME_FIELD = "email"`.
Введи, например, `admin@mail.ru` и пароль. Пароль при вводе не отображается,
это нормально.

## Шаг 4. Запустить сервер

```bash
python manage.py runserver
```

Это окно терминала больше не трогаем, сервер должен работать. Все дальнейшие
команды — **во втором окне** (не забудь и там `source venv/bin/activate`).

Должно быть написано `Starting development server at http://127.0.0.1:8000/`.

## Шаг 5. Проверить админку

Открыть в браузере http://127.0.0.1:8000/admin/ и войти под тем email и паролем,
что вводил в шаге 3.

Внутри будет раздел **Users** с одним пользователем и раздел **Todos** — пока пустой.
Оставь вкладку открытой, вернёмся сюда в шаге 12.

## Как работать в Postman

Дальше у каждого шага два способа: `curl` в терминале и то же самое в Postman.
Делать нужно что-то одно, результат одинаковый.

**Важно:** нужен **десктопный** Postman. Веб-версия в браузере не может достучаться
до `127.0.0.1` — это адрес твоего же компьютера, а сайт Postman работает на чужом
сервере. Если пользуешься вебом, придётся ставить Postman Desktop Agent.

Сервер в терминале всё равно должен работать. Postman его не заменяет, он только
отправляет запросы.

Один запрос собирается всегда одинаково:

1. **New** (или `+` на панели вкладок) → откроется пустой запрос
2. Слева от адресной строки — **выпадающий список метода**. По умолчанию GET,
   меняется на POST, PATCH, PUT, DELETE
3. В **адресную строку** вставить URL целиком, вместе с `http://`
4. Если нужно тело — вкладка **Body** под адресной строкой → выбрать
   переключатель **x-www-form-urlencoded** → появится таблица KEY / VALUE,
   заполнить построчно
5. Если нужен токен — вкладка **Headers** → добавить строку с ключом
   `Authorization` и значением `Token <ключ>`
6. Кнопка **Send**

Ответ появится внизу. **Код статуса** (`200 OK`, `401 Unauthorized`) — справа над
телом ответа, рядом со временем и размером. Отдельно просить его не нужно, поэтому
флаг `-i` из curl в Postman не переводится.

Пустые строки в Body и Headers ни на что не влияют — Postman отправляет только те,
у которых слева стоит **галочка**. Если запрос ведёт себя не так, как ждёшь,
первым делом проверь галочки.

## Шаг 6. Дверь закрыта

```bash
curl -i http://127.0.0.1:8000/api/todos/
```

**В Postman:**

| Что | Значение |
|---|---|
| Метод | **GET** |
| Адрес | `http://127.0.0.1:8000/api/todos/` |
| Body | не трогать |
| Headers | не трогать |

Ожидается `401 Unauthorized` и текст про отсутствие данных для входа.
Пока никто не представился — задачи не показывают.

Это важно сделать **до** регистрации, пока Postman ещё не запомнил никаких
заголовков. Показывает, что дверь закрыта по умолчанию.

## Шаг 7. Регистрация первого пользователя

```bash
curl -X POST http://127.0.0.1:8000/api/register/ \
  -d "email=vasya@mail.ru&password=Tr0ub4dour-x9&password2=Tr0ub4dour-x9"
```

**В Postman:**

| Что | Значение |
|---|---|
| Метод | **POST** |
| Адрес | `http://127.0.0.1:8000/api/register/` |
| Body | **x-www-form-urlencoded** |

Таблица в Body:

| KEY | VALUE |
|---|---|
| email | vasya@mail.ru |
| password | Tr0ub4dour-x9 |
| password2 | Tr0ub4dour-x9 |

Обрати внимание: в curl всё это записано одной строкой через `&`, а в Postman
каждое поле — своя строка. `&` это просто разделитель, ничего больше.

Ответ `201 Created`:

```json
{"email":"vasya@mail.ru","token":"..."}
```

**Выделить токен мышкой и скопировать** — дальше он нужен постоянно. Удобно
завести текстовый файл и складывать туда токены, чтобы не терять.

Пароля в ответе нет, хотя мы его отправляли. Так и задумано.

## Шаг 8. Проверить валидацию

Три ошибки подряд, все на одном и том же адресе `/api/register/` методом **POST**.
В Postman удобно не создавать три запроса, а менять значения в той же таблице Body
и жать Send заново.

**Пароли не совпадают:**

```bash
curl -X POST http://127.0.0.1:8000/api/register/ \
  -d "email=oshibka@mail.ru&password=Tr0ub4dour-x9&password2=Drugoy-parol-77"
```

| KEY | VALUE |
|---|---|
| email | oshibka@mail.ru |
| password | Tr0ub4dour-x9 |
| password2 | Drugoy-parol-77 |

Ожидается `400` и `{"password":["Пароли не совпадают."]}`.

**Слабый пароль:**

```bash
curl -X POST http://127.0.0.1:8000/api/register/ \
  -d "email=oshibka@mail.ru&password=123&password2=123"
```

| KEY | VALUE |
|---|---|
| email | oshibka@mail.ru |
| password | 123 |
| password2 | 123 |

Ожидаются три ошибки сразу: короткий, частый, только из цифр.

**Занятый email** — вернуть значения из шага 7 (`vasya@mail.ru` и одинаковые
пароли) и отправить второй раз. Придёт
`{"email":["user with this email address already exists."]}`.

## Шаг 9. Вход по email

```bash
curl -X POST http://127.0.0.1:8000/api/token/ \
  -d "username=vasya@mail.ru&password=Tr0ub4dour-x9"
```

**В Postman:**

| Что | Значение |
|---|---|
| Метод | **POST** |
| Адрес | `http://127.0.0.1:8000/api/token/` |
| Body | **x-www-form-urlencoded** |

| KEY | VALUE |
|---|---|
| username | vasya@mail.ru |
| password | Tr0ub4dour-x9 |

Поле называется `username`, но вписываем в него **email** — имя поля зашито
в готовом эндпоинте DRF, а модель ищет человека по email.

Токен придёт **тот же самый**, что при регистрации. Можно сравнить глазами
с тем, что скопировал в шаге 7.

## Шаг 10. Создать задачи

Подставить свой токен вместо `ТОКЕН_ВАСИ`:

```bash
curl -X POST http://127.0.0.1:8000/api/todos/ \
  -H "Authorization: Token ТОКЕН_ВАСИ" -d "title=Купить хлеб"

curl -X POST http://127.0.0.1:8000/api/todos/ \
  -H "Authorization: Token ТОКЕН_ВАСИ" -d "title=Сделать домашку"
```

**В Postman.** Здесь впервые появляется токен, поэтому добавляется вкладка Headers:

| Что | Значение |
|---|---|
| Метод | **POST** |
| Адрес | `http://127.0.0.1:8000/api/todos/` |
| Headers | ключ `Authorization`, значение `Token ЗДЕСЬ_ТОКЕН_ВАСИ` |
| Body | **x-www-form-urlencoded** |

| KEY | VALUE |
|---|---|
| title | Купить хлеб |

Как заполнять Headers: открыть вкладку **Headers**, в пустой строке внизу
в колонку KEY написать `Authorization`, в колонку VALUE — слово `Token`, **пробел**,
и вставить скопированный ключ. Целиком получается вроде:

```
Token 9c4f7a2e1b8d3f6a0c5e7d9b2a4f6c8e0d1b3a5f
```

Слово `Token` обязательно, пробел ровно один. Это самая частая ошибка: без них
придёт `401`, хотя ключ правильный.

Отправить, потом поменять в Body `title` на `Сделать домашку` и отправить ещё раз.
Каждая вернёт `201` и объект с `id`. **Запомнить `id` первой задачи** — понадобится
в шагах 11 и 13.

Посмотреть список:

```bash
curl http://127.0.0.1:8000/api/todos/ -H "Authorization: Token ТОКЕН_ВАСИ"
```

В Postman: тот же адрес, метод **GET**, Headers оставить, Body не нужен.
Придут две задачи.

## Шаг 11. Второй пользователь и распределение

Сначала зарегистрировать Петю — это шаг 7 с другим email:

```bash
curl -X POST http://127.0.0.1:8000/api/register/ \
  -d "email=petya@mail.ru&password=Tr0ub4dour-x9&password2=Tr0ub4dour-x9"
```

| KEY | VALUE |
|---|---|
| email | petya@mail.ru |
| password | Tr0ub4dour-x9 |
| password2 | Tr0ub4dour-x9 |

**Токен Пети — другой**, не такой как у Васи. Скопировать отдельно и не перепутать.

Создать задачу уже под ним:

```bash
curl -X POST http://127.0.0.1:8000/api/todos/ \
  -H "Authorization: Token ТОКЕН_ПЕТИ" -d "title=Задача Пети"
```

В Postman: метод **POST**, адрес `/api/todos/`, в Headers **заменить** значение
`Authorization` на токен Пети, в Body `title` = `Задача Пети`.

Теперь самое главное — **список Пети**:

```bash
curl http://127.0.0.1:8000/api/todos/ -H "Authorization: Token ТОКЕН_ПЕТИ"
```

Метод **GET**, тот же адрес, в Headers токен Пети.

Придёт одна задача, своя. Задач Васи не видно, хотя они лежат в той же таблице
базы данных.

Попробовать залезть в чужую по номеру — подставить `id` задачи Васи из шага 10:

```bash
curl -i http://127.0.0.1:8000/api/todos/1/ -H "Authorization: Token ТОКЕН_ПЕТИ"
```

| Что | Значение |
|---|---|
| Метод | **GET** |
| Адрес | `http://127.0.0.1:8000/api/todos/1/` |
| Headers | `Authorization` со значением `Token ТОКЕН_ПЕТИ` |

`404 Not Found`. Не `403` — сервер не подтверждает, что такая задача вообще есть.

Чтобы стало совсем наглядно, можно тут же поменять в Headers токен обратно на
Васин и отправить тот же запрос — придёт `200` и задача. Один и тот же адрес,
разные токены, разный результат.

## Шаг 12. Посмотреть глазами в админке

Вернуться на вкладку http://127.0.0.1:8000/admin/ и обновить.

В **Users** теперь три записи: admin, vasya, petya. В **Todos** — три задачи,
и у каждой в колонке владельца свой человек. Видно, что данные лежат вперемешку
в одной таблице, а разделяет их только фильтр по владельцу в коде.

## Шаг 13. Остальные методы

Все три запроса — по **своей** задаче Васи, адрес один и тот же, меняется только
метод и тело. В Postman удобно менять их в одной вкладке, не создавая новых.
Везде в Headers должен стоять токен Васи.

**PATCH — отметить выполненной:**

```bash
curl -X PATCH http://127.0.0.1:8000/api/todos/1/ \
  -H "Authorization: Token ТОКЕН_ВАСИ" -d "completed=true"
```

| Что | Значение |
|---|---|
| Метод | **PATCH** |
| Адрес | `http://127.0.0.1:8000/api/todos/1/` |
| Headers | `Authorization` = `Token ТОКЕН_ВАСИ` |
| Body | **x-www-form-urlencoded** |

| KEY | VALUE |
|---|---|
| completed | true |

В ответе `completed` стало `true`, а `title` остался прежним.

**PUT — заменить целиком:**

```bash
curl -X PUT http://127.0.0.1:8000/api/todos/1/ \
  -H "Authorization: Token ТОКЕН_ВАСИ" -d "title=Купить хлеб и молоко"
```

| Что | Значение |
|---|---|
| Метод | **PUT** |
| Адрес | тот же |
| Body | **x-www-form-urlencoded** |

В таблице Body **убрать галочку** со строки `completed` и добавить строку:

| KEY | VALUE |
|---|---|
| title | Купить хлеб и молоко |

Вот тут самое интересное. Посмотреть на ответ: `completed` снова `false`,
хотя мы его не трогали и только что ставили `true`.

Это и есть разница между PATCH и PUT. PATCH правит **только присланные поля**.
PUT заменяет **всю запись целиком**, а всё, что не прислали, берётся по умолчанию —
поэтому `completed` вернулось к `false`.

**DELETE — удалить:**

```bash
curl -i -X DELETE http://127.0.0.1:8000/api/todos/1/ \
  -H "Authorization: Token ТОКЕН_ВАСИ"
```

| Что | Значение |
|---|---|
| Метод | **DELETE** |
| Адрес | тот же |
| Headers | `Authorization` = `Token ТОКЕН_ВАСИ` |
| Body | не нужен |

`204 No Content`. Тела в ответе нет — в Postman окно ответа будет пустым, это
нормально, а не ошибка. Так и должно быть: «сделано, показывать нечего».

Отправить тот же запрос методом **GET** — придёт `404`, задачи больше нет.

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| `Connection refused` | сервер не запущен, вернуться к шагу 4 |
| `That port is already in use` | шаг 0, убить старые серверы |
| `401` с токеном | проверить, что в заголовке есть слово `Token` и пробел после него |
| `404` на всё | потерялся слеш в конце адреса или префикс `/api/` |
| `InconsistentMigrationHistory` | база от старой модели юзера, выполнить шаг 2 |
| `no such table` | не выполнен `migrate`, шаг 2 |
