# todo-drf

Простое API для списка задач на Django REST Framework. Учебное, разбирался с APIView.

Задача это title, completed и created_at, больше ничего.
Вьюхи написаны на APIView, а не на ViewSet — специально, чтобы руками расписать все методы.

Пользователь свой: `users.CustomUser`, вход по email вместо username.
Авторизация по токену, задачи видит только их владелец.

## Запуск

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

`createsuperuser` спросит **email**, а не username — так работает `USERNAME_FIELD = "email"`.

## Ручки

```
POST   /api/register/    регистрация, отдаёт токен
POST   /api/token/       вход по email и паролю, отдаёт токен

GET    /api/todos/       список своих задач
POST   /api/todos/       создать задачу
GET    /api/todos/1/     одна задача
PUT    /api/todos/1/     заменить целиком
PATCH  /api/todos/1/     обновить часть полей
DELETE /api/todos/1/     удалить
```

Первые две открыты всем, остальные только с токеном.

# Как это работает (шпаргалка, потом удалить)

## Что такое токен

Аналогия — браслет в аквапарке. На входе один раз показываешь паспорт и платишь,
тебе выдают браслет с номером. Дальше у каждой горки охранник паспорт не спрашивает,
он смотрит на браслет и сверяется со списком: браслет №4471 — это Иванов, оплачен день.

| В аквапарке | В проекте |
|---|---|
| паспорт | email + пароль |
| касса на входе | `POST /api/register/` или `/api/token/` |
| браслет | токен, 40 случайных символов |
| список у охранника | таблица `authtoken_token` в базе |
| горки внутри | `/api/todos/` |

Что реально лежит в базе после входа — три поля, больше ничего:

```
key     = 9c4f7a2e1b8d3f6a0c5e7d9b2a4f6c8e0d1b3a5f
user_id = 4
created = 2026-08-13 06:35
```

Главное: **внутри токена нет ни email, ни пароля**. Это случайная строка.
Связь «токен → человек» хранится на сервере, в этой таблице. По перехваченному
токену пароль восстановить нельзя — там нечего восстанавливать.

## Что происходит при каждом запросе

1. Клиент шлёт заголовок `Authorization: Token 9c4f7a2e…`
2. Сервер берёт строку после слова `Token`, ищет её в таблице, получает `user_id`.
   Этот пользователь попадает в `request.user`.
3. Вьюха делает `Todo.objects.filter(owner=request.user)` — отдаются задачи
   только этого человека, чужие в выборку не попадают никогда.
4. Токена нет или он неверный → `401`, до кода вьюхи выполнение не доходит.

## Зачем это вместо логина с паролем каждый раз

- **Пароль передаётся реже.** Один раз при входе, а не в каждом из сотен запросов.
- **Токен можно отозвать.** Утёк — удалил строку в таблице, человек логинится заново.
  С паролем пришлось бы менять сам пароль.
- **Проверка дешевле.** Сверить токен — один поиск по индексу. Проверить пароль —
  намеренно медленное хеширование, в базе видно `pbkdf2_sha256$1200000$`,
  то есть 1 200 000 итераций. Гонять такое на каждый запрос нельзя.

# Демонстрация в Postman

Сервер должен быть запущен: `python manage.py runserver`.
Тело запросов — вкладка **Body** → **x-www-form-urlencoded**.

Слеш в конце адреса обязателен: `/api/todos/` работает, `/api/todos` — нет.

## 1. Регистрация

```
POST http://127.0.0.1:8000/api/register/
```

Body:

| ключ | значение |
|---|---|
| email | student@mail.ru |
| password | Tr0ub4dour-x9 |
| password2 | Tr0ub4dour-x9 |

Ответ `201 Created`:

```json
{
    "email": "student@mail.ru",
    "token": "9c4f7a2e1b8d3f6a0c5e7d9b2a4f6c8e0d1b3a5f"
}
```

**Скопировать токен** — нужен в шагах 5–7.

Сказать: регистрация сразу возвращает токен, чтобы не делать второй запрос на вход.
Пароль в ответе не появляется — в сериализаторе оба поля пароля помечены `write_only`.

## 2. Пароли не совпадают

Тот же адрес, но `password2` другой. Ответ `400`:

```json
{
    "password": ["Пароли не совпадают."]
}
```

Заодно можно показать слабый пароль — вписать в оба поля `123`, получится три ошибки
сразу: слишком короткий, слишком частый, только из цифр. Это стандартные валидаторы
Django из настройки `AUTH_PASSWORD_VALIDATORS`.

## 3. Запрос без токена

```
GET http://127.0.0.1:8000/api/todos/
```

Никаких заголовков — в этом смысл шага. Ответ `401 Unauthorized`:

```json
{
    "detail": "Authentication credentials were not provided."
}
```

Сказать: все эндпоинты закрыты по умолчанию, в настройках прописано
`DEFAULT_PERMISSION_CLASSES: [IsAuthenticated]`. Доступ открывается осознанно —
у регистрации стоит `AllowAny`, иначе зарегистрироваться мог бы только тот,
кто уже зарегистрирован.

## 4. Повторный вход

```
POST http://127.0.0.1:8000/api/token/
```

Body:

| ключ | значение |
|---|---|
| username | student@mail.ru |
| password | Tr0ub4dour-x9 |

Ответ `200 OK` — токен **тот же самый**, что при регистрации: он создаётся один раз
и живёт, пока его не удалят.

Поле называется `username`, а внутрь кладём email — так устроен готовый эндпоинт DRF,
имя поля у него зашито. Но в проекте своя модель пользователя с `USERNAME_FIELD = "email"`,
поэтому Django ищет человека именно по email. Это не ошибка, а стык стандартного кода
с кастомной моделью.

## 5. Создать задачу с токеном

```
POST http://127.0.0.1:8000/api/todos/
```

Headers:

| ключ | значение |
|---|---|
| Authorization | Token 9c4f7a2e1b8d3f6a0c5e7d9b2a4f6c8e0d1b3a5f |

Body:

| ключ | значение |
|---|---|
| title | Сделать домашку |

Ответ `201 Created`:

```json
{
    "id": 1,
    "title": "Сделать домашку",
    "completed": false,
    "created_at": "2026-08-13T06:20:27.827558Z"
}
```

Поле `owner` в запросе не передавалось. Владельца сервер проставил сам из токена —
в коде это `serializer.save(owner=request.user)`. Подделать чужое авторство через
тело запроса невозможно.

## 6. Список своих задач

```
GET http://127.0.0.1:8000/api/todos/
```

С тем же заголовком `Authorization`. Ответ `200 OK` со своей задачей в списке.

## 7. Второй пользователь чужого не видит

Самый убедительный шаг — показывает, что разграничение доступа реально работает.

Зарегистрировать второго (шаг 1 с другим email, например `petya@mail.ru`),
взять **его** токен и повторить с ним:

```
GET /api/todos/        ->  200 OK,  []          пусто
GET /api/todos/1/      ->  404 Not Found
```

Сказать: пустой список — потому что выборка фильтруется по владельцу. А на прямой
запрос чужой задачи приходит `404`, а не `403`, и это намеренно: `403` означал бы
«задача существует, но она не твоя» и подтвердил бы постороннему сам факт её
существования. `404` не выдаёт ничего.

## Если что-то не работает

| Симптом | Причина |
|---|---|
| `401` с токеном | потерялось слово `Token` или пробел. Формат строго: `Token 9c4f7a2e…` |
| `401` без заголовка | заголовок добавляется в **Headers**, не в Body. Проверить галочку слева от строки |
| `400` при регистрации | читать тело ответа, там написано какое поле не устроило |
| `404` на всё | потерялся слеш в конце или префикс `/api/` |
| Connection refused | не запущен `python manage.py runserver` |

## Готовая коллекция для Postman

Чтобы не вбивать запросы руками, рядом лежит `postman_collection.json`.

В Postman: **Import** → перетащить файл → появится коллекция `todo-drf` из двух папок.
Дальше просто жать **Send** сверху вниз. Токены и id задачи подставляются сами,
копировать из ответа в заголовок не нужно.

У каждого запроса на вкладке **Tests** написаны проверки, поэтому после Send внизу
видно **Test Results** с зелёными галочками: «Статус 201 Created», «Пароль в ответе
не светится», «Список пустой — чужого не видно». Это удобно показывать: не просто
пришёл какой-то ответ, а пришёл именно ожидаемый.

Можно запустить всё разом: **Runner** → перетащить коллекцию → **Run**. Прогонит все
13 запросов и покажет сводку.

Email при регистрации генерируется с меткой времени (`student1755066000000@mail.ru`),
чтобы коллекцию можно было прогонять повторно — иначе второй раз упёрлось бы
в «email уже занят».

```

```

Тесты гоняются на отдельной временной базе, `db.sqlite3` они не трогают.

## Заметки

- id и created_at только на чтение, руками не задаются
- база sqlite, лежит рядом и в репу не коммитится
- кастомный юзер сделан по статье testdriven.io/blog/django-custom-user-model, вариант AbstractUser
- модель юзера меняется только до первой миграции, иначе Django ругается на несовместимость
